# VeloVibe AI — велокопілот і кабінет райдера

Україномовний велокабінет для налаштування велосипеда, аналізу геометрії, перевірки сумісності компонентів і пошуку місць для катання в Україні.

## Запуск локально

Потрібен Node.js, сумісний із Vite 8.

1. Встанови залежності: `npm install`
2. Скопіюй `.env.example` у `.env` та заповни Supabase URL і публічний ключ. Серверний `SUPABASE_SERVICE_ROLE_KEY` зберігай лише на сервері. Додай `GEMINI_API_KEY`, щоб увімкнути відповіді Gemini; без нього сервер використовує обмежені довідкові відповіді.
3. Запусти застосунок: `npm run dev`
4. Відкрий адресу, яку виведе сервер (типово `http://localhost:3000`).

## Підготовка Supabase

- У Supabase Dashboard створи проєкт і скопіюй Project URL та publishable/anon key у `VITE_SUPABASE_URL` і `VITE_SUPABASE_ANON_KEY`.
- Додай `SUPABASE_SERVICE_ROLE_KEY` як серверний секрет. Він має повний доступ до проєкту й ніколи не повинен мати префікс `VITE_`, потрапляти в браузер або комітитися.
- Встанови `OWNER_EMAIL` на адресу першого адміністратора. Сервер зможе надати роль лише після підтвердження цієї пошти в Supabase Auth.
- Після підтвердження першого власника серверний маршрут `POST /api/auth/bootstrap-admin` перевіряє Supabase access token і призначає роль `admin`; після призначення клієнт має оновити Supabase session, щоб отримати новий JWT.
- Виконай SQL-міграцію `supabase/migrations/202611120001_initial_community_schema.sql` у SQL Editor Supabase. Вона створює профілі, споти та приватні AI-розмови з політиками RLS.
- Після неї виконай `supabase/migrations/202611130001_support_and_advertising.sql` для звернень райдерів до адміна, рекламних місць, зображень у Storage та відповідних RLS-політик.
- У Supabase Auth увімкни підтвердження пошти, налаштуй SMTP для production і додай локальну й production URL-адреси до Site URL / Redirect URLs.
- Після входу райдер заповнює первинний профіль; зміни з гаража зберігаються у власному рядку `profiles`. Адміністратор отримує вкладку «Адмінка», де додані точки спершу мають статус `pending` і з’являються на мапі лише після ручної перевірки.
- Збереження історії AI вимкнене за замовчуванням і вмикається лише за згодою під час onboarding або в чаті. Вимкнення стирає збережені розмови цього акаунта; RLS обмежує їх власником.
- Райдер може видалити акаунт у «Гараж & Налаштування» з явним підтвердженням; Supabase Auth видаляє користувача, а залежні профіль/чати очищуються каскадно.
- Ключі API не приймаються через браузерну адмінку: додай їх у серверні секрети середовища й перезапусти сервер. Так service-role та Gemini ключі не потраплять у браузер.
- Для погоди (Open-Meteo) та карти OSM/Overpass окремі API-ключі не потрібні. Gemini API — необов’язковий; його ключ задається тільки серверною змінною `GEMINI_API_KEY`.

## Публікація на Render

У репозиторії є `render.yaml` для web service на Node.js. Створи Render Blueprint із репозиторію, додай захищені значення змінних, позначених `sync: false`, і розгорни сервіс. Render виконає `npm ci`, TypeScript-перевірку та production build; health check використовує `/api/velovibe/health`. Додай отриманий HTTPS-домен до Supabase Auth Site URL і Redirect URLs, а також налаштуй SMTP для підтвердження email та відновлення пароля. Публічний домен і ключ Gemini ніколи не треба вбудовувати в код.

## Логотипи та зображення бренду

Логотипи розміщуй у `public/brand/` з такими назвами:

| Файл | Де відображається |
|---|---|
| `site-logo.png` | Навігація, вхід, реєстрація, профіль першого запуску |
| `ai-logo.png` | Плаваюча кнопка AI-копілота |
| `support-logo.png` | Плаваюча кнопка звернення до адміністрації |
| `team-logo.png` | Нижній колонтитул біля назви команди |

PNG із прозорим фоном рекомендований; квадратні файли 512×512 px або більші підійдуть для логотипів. Якщо PNG ще немає, сайт автоматично покаже SVG-заготовку з такою самою назвою без `.png`. Не видаляй SVG-заготовки, якщо плануєш користуватися fallback.

Рекламні банери не клади до `public/brand/`: адміністратор завантажує їх через керування рекламою, а файли зберігаються у Supabase Storage.

## Google AdSense

AdSense показується лише після налаштування ID видавця та окремих рекламних блоків для кабінету й мапи. У Google AdSense створи обліковий запис і два responsive display ad units, потім задай у локальному `.env` або Render environment:

| Змінна | Значення |
|---|---|
| `VITE_ADSENSE_CLIENT_ID` | ID видавця на кшталт `ca-pub-1234567890123456` |
| `VITE_ADSENSE_DASHBOARD_SLOT` | Числовий ad slot ID для кабінету |
| `VITE_ADSENSE_SPOTS_SLOT` | Числовий ad slot ID для сторінки спотів |

ID видавця й слотів не є секретами. Поки їх не задано, AdSense-скрипт не завантажується. Для показу реклами сайт має бути схвалений Google AdSense і відповідати його правилам; додай production-домен у налаштуваннях AdSense та виконай вимоги щодо ads.txt, якщо їх покаже кабінет. Для персоналізованої реклами користувачам з ЄЕЗ, Великої Британії та Швейцарії Google вимагає сертифіковану CMP; налаштуй її в AdSense до обслуговування аудиторії з цих регіонів.

Потрібні змінні:

| Змінна | Де використовується | Призначення |
|---|---|---|
| `VITE_SUPABASE_URL` | браузер | URL Supabase-проєкту |
| `VITE_SUPABASE_ANON_KEY` | браузер | Публічний ключ Supabase; доступ обмежує RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | тільки сервер | Перевірка користувачів і безпечне початкове призначення ролі |
| `OWNER_EMAIL` | тільки сервер | Підтверджена адреса першого адміністратора |
| `GEMINI_API_KEY` | тільки сервер, необов’язково | Gemini AI |
| `VITE_ADSENSE_CLIENT_ID` | браузер, необов’язково | ID видавця Google AdSense |
| `VITE_ADSENSE_DASHBOARD_SLOT` | браузер, необов’язково | Рекламний блок у кабінеті |
| `VITE_ADSENSE_SPOTS_SLOT` | браузер, необов’язково | Рекламний блок на мапі |
| `PORT` | сервер, необов’язково | Порт HTTP-сервера |

Погода вибирається окремо від мапи: місто райдера або геолокація за окремим дозволом браузера. Точне місце з геолокації не зберігається у localStorage.

## Дані погоди й веломісць

- Поточні погодні умови завантажуються через серверний endpoint `/api/velovibe/weather` з Open-Meteo (температура, відчутна температура, вологість, опади та вітер). API-ключ не потрібен; відповіді кешуються на 10 хвилин, ручне оновлення запитує свіжі дані. Це модельні поточні умови, а не гарантовані вимірювання метеостанції або стан трейлу.
- Веломісця запитуються з OpenStreetMap через Overpass API й кешуються на 10 хвилин; ручне оновлення повторно запитує джерело. У мапі відображаються лише записи з координатами, назвою та посиланням на першоджерело. Центр контуру може не збігатися з входом; доступність і стан траси не підтверджуються.
- Публічний Overpass API може бути перевантажений. У такому разі застосунок показує помилку й не підміняє відсутні дані вигаданими точками.
- Початкова точка мапи `49.2483278, 28.4292258` взята з наданого Google Maps-посилання та є лише центром перегляду.
- Логотипи VeloVibe та окремі AI/підтримки — локальні SVG-ресурси. Партнерські банери показуються лише після ручної активації адміністратором; без рекламодавця UI лишає позначене місце без фальшивих оголошень.
